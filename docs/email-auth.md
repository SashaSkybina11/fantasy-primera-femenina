# Подтверждение почты и восстановление пароля

## Подключение Resend

1. Создайте аккаунт Resend и добавьте принадлежащий вам домен в Domains.
2. Добавьте указанные Resend DNS-записи у регистратора и дождитесь статуса Verified.
3. Создайте API-ключ с правом отправки писем для этого домена.
4. В настройках окружения сервера (Vercel → Project → Settings → Environment Variables) задайте:
   - `RESEND_API_KEY` — секретный ключ Resend. Не добавляйте его в Git, чат или переменные `VITE_*`.
   - `EMAIL_FROM` — например `Fantasy Futsal <noreply@ваш-домен>`.
   - `FRONTEND_URL` — полный HTTPS-адрес сайта. Ссылки восстановления строятся только из него.
   - Сохраните существующие `DATABASE_URL` и `JWT_SECRET`. Изменять их для подключения почты не нужно.
   - Для совместного развёртывания frontend и API оставьте `VITE_API_URL` незаданным: приложение использует `/api` на том же домене. Не переносите локальное значение `http://localhost:4000/api` в Vercel.
   - Задайте переменные для нужного окружения Vercel (Production; при проверке Preview — отдельно) и сделайте Redeploy после сохранения.
5. Выполните штатное развёртывание. `vercel-build` применяет миграции; для другого хостинга сначала выполните `npm run prisma:migrate:deploy -w backend`, затем `npm run build`.
6. Проверьте настоящую регистрацию на своей почте, повторную отправку и восстановление пароля. Убедитесь, что письма доходят, включая папку «Спам».

Документация провайдера: https://resend.com/docs/dashboard/domains/introduction и https://resend.com/docs/api-reference/emails/send-email.

Пример отправителя: если вам принадлежит `example.com`, подтвердите в Resend домен `mail.example.com` и используйте `EMAIL_FROM="Fantasy Futsal <noreply@mail.example.com>"`. Это только пример: домен должен быть вашим, а адрес — внутри подтверждённого домена. Поддомен `*.vercel.app` для этого не подходит, поскольку его DNS вам не принадлежит. Resend покажет конкретные записи DKIM/SPF/MX; копируйте значения из его панели, не подставляйте вымышленные. Настройки входящей почты основного домена менять не нужно при использовании отдельного поддомена.

В `vercel.json` длительность API-функции увеличена до 30 секунд: это оставляет время на БД, хеширование пароля и запрос к Resend с тайм-аутом 10 секунд. Миграция email-auth только добавляет поля и две таблицы; существующие строки пользователей и игровые данные не удаляет. На рабочей БД не запускайте reset/seed для включения почты.

Без настройки отправителя регистрация возвращает понятную ошибку отправки. Обхода подтверждения в production нет. Изменения кода сами по себе не включают доставку писем.

## Поведение

- Регистрация сохраняет временную заявку с хешем пароля; аккаунт, команда и членство в лиге создаются атомарно после подтверждения шестизначного кода.
- Код действует 10 минут, допускается 5 попыток; повторная отправка заменяет предыдущий код. Между отправками — минимум 60 секунд, максимум 5 отправок за час на адрес.
- Незавершённую регистрацию можно продолжить после обновления страницы. Браузер хранит только адрес почты и время следующей отправки, не пароль и не код. Через сутки нужно начать заново.
- Восстановление использует случайный одноразовый токен на 30 минут. GET ссылки ничего не меняет: требуется отправка формы нового пароля. Повторный запрос заменяет старую ссылку.
- Ответ восстановления одинаков для существующего и неизвестного адреса. Ошибки доставки восстановления фиксируются на сервере без адресов, кодов и содержимого писем.
- В БД хранятся только HMAC-хеши кодов и токенов. Секрет ссылки находится в URL-фрагменте, а не в query string.
- Ограничения запросов хранятся в PostgreSQL и действуют между экземплярами сервера. Старые записи ограничений и заявок удаляются при последующих запросах с запасом в сутки.
- Сброс и смена пароля увеличивают версию сеанса; прежние JWT и ссылки восстановления становятся недействительными. Для прежних JWT без версии используется версия 0.
- Существующие пользователи не блокируются: их `emailVerifiedAt` остаётся пустым до восстановления пароля. Все новые регистрации требуют подтверждения почты.

## Проверки

`npm run test:email-auth` создаёт отдельную временную БД только на localhost, применяет миграции и проверяет HTTP-сценарии с подменой доставки Resend. Настоящие письма не отправляются. Основная БД не изменяется.

`node tests/email-auth-ui.mjs` проверяет формы и адаптивность через Playwright при запущенном frontend (`TEST_BASE_URL`, по умолчанию `http://127.0.0.1:5173`).

Проверяются украинский, испанский и английский языки, светлая и тёмная темы, ширины 320 и 1440 px: ожидание ответа, ошибка доставки, неверный/неполный код, задержка после обновления страницы, повторная отправка, истёкшая регистрация, лимит запросов, отправленная ссылка, истёкшая ссылка, успешная смена пароля и повреждённая ссылка. Все API-запросы перехвачены, письма не отправляются. Результат сохраняется в `artifacts/email-auth/ui-results.json`.
